# host-arduino-core 要件定義書

## 1. 目的

`host-arduino-core` は、Arduino スケッチの純粋なロジック部分をホスト PC 上でビルド、起動、テストできるようにするための Arduino Core および Boards Manager パッケージである。

本パッケージは物理 Arduino 互換ボードを対象とせず、テスト実行環境としてホスト OS 上の実行ファイルを生成、起動することを目的とする。

## 2. 想定利用者

- Arduino ライブラリまたはスケッチのロジック部分を自動テストしたい開発者。
- `pytest-embedded-arduino-cli` などの Arduino CLI 対応ホスト側テストフレームワークから Arduino スケッチ相当のプログラムを起動し、入出力を検証したい開発者。
- 物理デバイスやシリアルポートに依存しない CI 環境で Arduino 向けコードを検証したい開発者。
- 実機が手元にない状態で、M5GFX / LovyanGFX / M5Unified などの画面描画を SDL2 上で手動確認したい開発者。

## 3. 対象環境

### 3.1 対応 OS

最低限、以下の OS で動作すること。

- Windows
- Linux
- macOS

### 3.2 前提ツール

利用者のホスト環境には、対象 OS 上で利用可能な `gcc` / `g++` 互換のビルド環境が存在すること。

本パッケージは、Boards Manager 経由でビルドツールを自動インストールしない。利用者は事前にホスト OS 側へ必要な `gcc` / `g++` 互換ツールチェーンを用意すること。

### 3.3 Arduino ツール

以下の Arduino CLI 操作に対応すること。

- `arduino-cli compile`
- `arduino-cli upload`

以下の Arduino CLI 操作は対象外とする。

- `arduino-cli monitor`

## 4. 基本要件

### 4.1 Boards Manager パッケージ

- Arduino Boards Manager からインストール可能なパッケージとして提供できること。
- Arduino CLI から core install 可能であること。
- Boards Manager のパッケージ名は `lang-ship` とすること。
- アーキテクチャ名は `host` とすること。
- 自動テスト用ボード ID は `host` とし、FQBN は `lang-ship:host:host` とすること。
- 手動表示確認用ボード ID は `display` とし、FQBN は `lang-ship:host:display` とすること。
- Core は `host` として提供すること。
- `host` と `display` は同一の `cores/host` を共有し、Arduino / ESP32 互換 API の実装を分岐させないこと。
- 個別の M5Stack / Core2 / CoreS3 などのボード ID は追加せず、`display` ボードのメニューと `sketch.yaml` の profile で扱うこと。
- パッケージには、ビルドとテスト実行に必要な最小限の Arduino Core を含めること。
- パッケージには、リリース配布に必要なメタデータを含めること。
- パッケージは、コンパイラやリンカなどのビルドツールを同梱または自動インストールしないこと。

### 4.2 ビルド

- `arduino-cli compile` により、ホスト OS 上で実行可能なプログラムを生成できること。
- ビルドにはホスト環境に存在する `gcc` / `g++` 互換コンパイラを利用すること。
- 生成されたプログラムは、物理ボードへの書き込みを必要とせず、ホスト OS 上で起動できること。
- Windows、Linux、macOS の各環境で同等のビルド操作が可能であること。

### 4.3 アップロード

- `arduino-cli upload` により、直前または指定されたビルド成果物をホスト OS 上で起動できること。
- `upload` は物理デバイスへの書き込みを行わないこと。
- `lang-ship:host:host` の `upload` は起動したプログラムの終了を待ち続けず、呼び出し元へ制御を戻すこと。
- `lang-ship:host:host` で起動されたプログラムは、テストフレームワークから接続および制御できる状態になること。
- `lang-ship:host:display` の `upload` は、生成されたプログラムを手動確認用に起動し、SDL2 画面を前面に表示できること。
- `lang-ship:host:display` で起動されたプログラムは、画面を閉じる、またはプロセスを終了することで終了できること。

### 4.4 実行プロセスの終了

- `lang-ship:host:host` の `upload` により起動されたプログラムは、テスト終了後に自動的に終了できること。
- `lang-ship:host:host` では、TCP 接続が確立されない状態が一定時間続いた場合、プログラムは自動終了できること。
- `lang-ship:host:host` では、TCP 接続が切断された場合、プログラムは自動終了できること。
- `lang-ship:host:host` の自動終了により、テスト失敗時やテスト中断時でも不要な実行プロセスが残り続けないこと。
- `lang-ship:host:display` では TCP 接続待ちを行わないこと。
- `lang-ship:host:display` では TCP 接続状態を終了条件にしないこと。
- `lang-ship:host:display` の終了は、SDL2 画面を閉じる、スケッチ自身が終了要求を出す、または利用者がプロセスを終了する操作を基本とすること。

## 5. Arduino Core 要件

### 5.1 最小 API

純粋なロジック部分のテストに必要な、最低限の Arduino API を提供すること。

対象 API には少なくとも以下を含めること。

- `setup()`
- `loop()`
- `Serial`
- 時刻取得または経過時間取得に関する基本 API
- 遅延に関する基本 API
- Arduino スケッチで一般的に利用される基本型、定数、マクロ

デジタル入出力およびアナログ入出力に関する API は、純粋なロジック部分のテストに必要な範囲で提供できればよく、必須の最小 API には含めない。

ただしデジタル入出力および SPI / I²C については、5.3 のバス観測要件を満たすこと。

### 5.2 実行モデル

- ホスト実行ファイルの起動時に `setup()` が呼び出されること。
- `setup()` 実行後、`loop()` が継続的に呼び出されること。
- テスト用途として、プログラムの終了条件を外部から成立させられること。

### 5.3 バス観測

スケッチがバスへ流した内容を、ライブラリ側やテスト側から観測し、応答を差し込める口を提供すること。

- 周辺機器の模型はコアに持ち込まないこと。デバイス固有のプロトコル解釈は、そのデバイスを扱うライブラリ側の責務とする。
- `digitalWrite` の書き込みを、登録された観測フックへ通知できること。
- `digitalRead` は、そのピンへ直前に書き込まれた値を返せること。
- 入力値を、ライブラリ側の模型またはテストから差し込めること。
- プルアップ / プルダウン付きの入力設定は、実機で読み取れる電位に相当する値を保持できること。
- SPI は転送された 1 バイトごとに観測でき、フックの戻り値を応答（MISO 相当）として扱えること。
- SPI のトランザクション設定（クロック、ビット順、データモード）を観測できること。
- I²C は初期化に成功し、既定ではデバイスが存在しない状態として振る舞えること。
- I²C は、アドレス、ペイロード、ストップ条件を含むトランザクション単位で観測でき、応答を差し込めること。
- 観測口は、電気的挙動、バスのタイミング、クロック速度を再現しないこと。
- 観測フックが未登録の場合、ビットバン経路の実行コストを実質的に増やさないこと。

### 5.4 非対象

以下は本 Core の主要目的から外れるため、必須要件に含めない。

- 実機 Arduino と完全互換のタイミング精度。
- 実機 Arduino と完全互換の GPIO 挙動。
- デジタル入出力およびアナログ入出力の完全な再現。
- 実機 Arduino と完全互換の割り込み、タイマ、電源管理、ブートローダ挙動。
- 実機シリアルポートへの対応。

## 6. 通信要件

### 6.1 通信方式

- `lang-ship:host:host` では、実行中プログラムとテストフレームワーク間の通信にローカルホスト上の TCP/IP 通信を利用すること。
- 物理または仮想シリアルポートは必須としないこと。
- TCP 通信は、同一ホスト内での自動テスト実行を前提とすること。
- TCP runtime は `lang-ship:host:host` 専用とし、`lang-ship:host:display` では提供しないこと。
- `lang-ship:host:display` は TCP 接続待ち、接続直後の settle 待ち、TCP 切断による終了を行わないこと。
- `lang-ship:host:display` の `Serial` 出力は手動確認向けに標準出力へ流すことを基本とすること。
- `lang-ship:host:display` の `Serial` 入力は必須要件に含めないこと。

### 6.2 Serial 入出力

- `lang-ship:host:host` では、Arduino スケッチから見た `Serial` 入出力を TCP 通信経由で扱えること。
- スケッチが `Serial` に出力した内容を、テスト側が TCP 接続経由で取得できること。
- テスト側から送信された入力を、スケッチ側が `Serial` 入力として取得できること。
- `setup()` 直後など、テスト側が TCP 接続する前に発生した `Serial` 出力も失われないこと。
- `lang-ship:host:display` では、`Serial.print()` / `Serial.println()` / `Serial.write()` の出力を標準出力へ表示できること。
- `lang-ship:host:display` では、TCP 接続前出力バッファを持たないこと。

### 6.3 出力バッファ

- `lang-ship:host:host` では、`Serial` 出力は TCP 接続前からバッファリングされること。
- TCP 接続後、テスト側はバッファリング済みの出力を取得できること。
- バッファにより、起動直後のログや初期化時の出力をテストで検証できること。
- 出力バッファには上限を設け、テスト対象プログラムの異常動作によりホスト側メモリを消費し続けないこと。
- `lang-ship:host:display` では、TCP 用の `Serial` 出力バッファを持たないこと。

### 6.4 接続情報の通知

- `lang-ship:host:host` では、実行中プログラムが待ち受ける TCP ポート番号を、標準出力から取得できること。
- `lang-ship:host:host` では、実行中プログラムが待ち受ける TCP ポート番号とプロセス ID を、実行ファイルの近傍に作成されるファイルから取得できること。
- テストフレームワークは、標準出力またはファイルのいずれかを使って接続先情報を取得できること。
- `pytest-embedded-arduino-cli` などのテストフレームワークが `upload` 実行時の標準出力を取得できる場合は、標準出力から TCP ポート番号を取得できること。
- 標準出力からの取得に失敗した場合や、OS ごとのプロセス起動差異がある場合に備え、接続情報ファイルを代替経路として利用できること。
- 接続情報ファイルは、ビルド成果物である実行ファイルと同じフォルダに作成されること。
- `lang-ship:host:display` では、TCP 接続情報ファイルを作成しないこと。
- `lang-ship:host:display` では、TCP ポート番号を標準出力へ通知しないこと。

### 6.5 TCP 接続モデル

- TCP 接続は、テスト用途として 1 実行プロセスにつき 1 クライアント接続を基本とすること。
- 複数クライアントからの同時接続は必須要件に含めない。
- `host` ボードでは、TCP 接続が確立した後に切断された場合、その実行プロセスは自動終了できること。
- `display` ボードは TCP 接続モデルの対象外とすること。

### 6.6 ランタイムログ

- `lang-ship:host:host` では、実行中プログラムは、標準入出力、TCP 待ち受け、TCP 接続、TCP 切断、終了理由を追跡できるログを出力すること。
- ランタイムログは、既定では実行ファイルと同じフォルダに作成されること。
- ランタイムログは、環境変数により無効化または出力先変更ができること。
- `Serial` の送受信内容そのものは既定ではログに出力せず、必要な場合でも明示的な設定を必要とすること。
- `lang-ship:host:display` では、TCP runtime ログを作成しないこと。

## 7. テスト連携要件

- `pytest-embedded-arduino-cli` などの Arduino CLI 対応外部テストフレームワークから利用しやすいこと。
- テストコードは、ビルド、起動、接続、入出力、終了確認の一連の流れを自動化できること。
- CI 環境での利用を想定し、GUI 操作や物理デバイス接続を必須にしないこと。
- テスト失敗時にも、後続テストに影響するプロセスやポート使用が残りにくいこと。

## 8. 手動表示確認要件

- 実機がない環境で、SDL2 を利用した画面表示を手動確認できること。
- 手動表示確認用の標準 FQBN は `lang-ship:host:display` とすること。
- `display` ボードは `host` ボードと同じ Core 実装を使い、Core API の対応差を作らないこと。
- `display` ボードは M5GFX / LovyanGFX / M5Unified の SDL2 バックエンドを利用できること。
- `display` ボードは、対象デバイス種別、表示倍率、回転などをボードメニューで選択できること。
- 個別デバイスごとのボード ID は追加しないこと。
- CLI での利用性は、サンプルごとの `sketch.yaml` profile に代表設定を用意することで補うこと。
- SDL2 画面を閉じると実行プロセスを終了できること。
- `M5_LOGE` / `M5_LOGW` / `M5_LOGI` / `M5_LOGD` / `M5_LOGV` など M5Unified の `M5.Log` 系出力は、手動確認時には標準出力へ表示されることを基本とすること。
- `display` ボードでは、SDL2 画面と標準出力のログ表示を分離して扱うこと。
- Windows などで標準出力コンソール表示が手動確認の妨げになる場合は、コンソール表示の有無を切り替えるボードメニューで対応できること。

## 9. 配布・リリース要件

- GitHub Releases などから Boards Manager 用パッケージを配布できること。
- Boards Manager index を公開できること。
- パッケージ生成、チェックサム算出、index 更新を自動化できること。
- タグまたは手動操作を起点にリリース処理を実行できること。

## 10. ドキュメント要件

- インストール方法を記載すること。
- Windows、Linux、macOS それぞれの前提環境を記載すること。
- Arduino CLI での compile と upload の利用方法を記載すること。
- TCP 経由での Serial 入出力の利用方法を記載すること。
- `arduino-cli monitor` が非対応であることを明記すること。
- 実機 Arduino ではなくテスト用ホスト実行環境であることを明記すること。
- `lang-ship:host:host` は自動テスト用、`lang-ship:host:display` は手動表示確認用であることを明記すること。
- M5GFX / LovyanGFX / M5Unified の SDL2 手動確認に必要な前提環境を記載すること。
- `M5_LOG*` は M5Unified の `M5.Log` 経由で標準出力へ出ることを記載すること。

## 11. 制約

- 本プロジェクトは実用的な Arduino 互換ボードの提供を目的としない。
- 実機ハードウェア固有機能の完全再現は目的としない。
- シリアルポート互換レイヤの提供は必須としない。
- `arduino-cli upload` はホスト上のプログラム起動を意味し、フラッシュ書き込みを意味しない。
- M5Stack 系デバイスごとの個別ボード ID を網羅することは目的としない。
- `display` ボードは手動確認用であり、GUI を必要とする表示テストを CI の必須要件にしない。

## 12. 受け入れ基準

- Windows、Linux、macOS の各環境で `arduino-cli compile` によりサンプルスケッチをビルドできること。
- `arduino-cli upload` により、ビルド済みプログラムをバックグラウンドで起動できること。
- 起動したプログラムの TCP 待ち受けポートを標準出力から取得できること。
- 起動したプログラムのプロセス ID と TCP 待ち受けポートをファイルから取得できること。
- 接続情報ファイルが実行ファイルと同じフォルダに作成されること。
- TCP 接続前に発生した `Serial` 出力を、接続後に取得できること。
- `Serial` 出力バッファが上限を持つこと。
- TCP 接続経由で `Serial` 入力をスケッチへ渡せること。
- 1 実行プロセスにつき 1 クライアント接続でテストを実行できること。
- `lang-ship:host:host` では、TCP 接続が確立されない場合、一定時間後にプログラムが自動終了すること。
- `lang-ship:host:host` では、TCP 接続が切断された場合、プログラムが自動終了すること。
- ランタイムログに TCP 接続、切断、終了理由が記録されること。
- `arduino-cli monitor` を必要とせずに、テスト側からログ取得と入力送信ができること。
- `lang-ship:host:display` で SDL2 を利用するサンプルスケッチをビルド、起動できること。
- `lang-ship:host:display` では、TCP 接続待ちを行わずに `setup()` / `loop()` が開始されること。
- `lang-ship:host:display` では、TCP 接続情報ファイルが作成されないこと。
- `lang-ship:host:display` では、`Serial` 出力が標準出力で確認できること。
- `lang-ship:host:display` で SDL2 画面を閉じたときに実行プロセスが終了すること。
- `lang-ship:host:display` で M5Unified の `M5_LOG*` 出力が標準出力で確認できること。
